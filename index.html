راهنمای جامع و کاربردی Git و GitHub

یک Cheat Sheet حرفه‌ای که از صفر شروع می‌شود و شما را قدم‌به‌قدم تا استفاده حرفه‌ای از Git و GitHub پیش می‌برد؛ همراه با مثال‌های واقعی برای پروژه‌های PHP روی XAMPP و ویرایش با VS Code در ویندوز. هر زمان چیزی یادتان رفت، کافی است به بخش مربوطه یا Cheat Sheet یک‌صفحه‌ای در انتها مراجعه کنید.

Windows VS Code XAMPP PHP · HTML · CSS · JS مبتدی تا حرفه‌ای
۱

مفاهیم پایه

قبل از هر دستوری، بهتر است این کلمات کلیدی را بشناسید. هرکدام را کوتاه و همراه با یک مثال واقعی توضیح داده‌ایم.

Git

نرم‌افزاری که روی کامپیوتر شما نصب می‌شود و تغییرات فایل‌های پروژه را در طول زمان ذخیره و مدیریت می‌کند.

مثال: وقتی یک خط کد را اشتباه پاک می‌کنید، با Git می‌توانید به نسخه قبلی فایل برگردید.

GitHub

یک سرویس آنلاین که پروژه‌های Git را روی اینترنت میزبانی می‌کند تا با دیگران همکاری کنید و نسخه پشتیبان آنلاین داشته باشید.

مثال: پروژه لوکال C:\xampp\htdocs\MyProject می‌تواند نسخه آنلاینش در github.com باشد.

Git در برابر GitHub

Git یک ابزار است و حتی بدون اینترنت هم کار می‌کند. GitHub یک پلتفرم است که از Git استفاده می‌کند (مشابه GitLab یا Bitbucket).

مثال: می‌توانید Git را فقط روی کامپیوتر خودتان، بدون هیچ اکانت GitHub، استفاده کنید.

Repository

پوشه‌ای که Git تاریخچه تغییراتش را دنبال می‌کند؛ به آن «Repo» هم می‌گویند.

مثال: پوشه MyProject شما بعد از اجرای git init به یک Repository تبدیل می‌شود.

Commit

یک «عکس فوری» از وضعیت فعلی فایل‌ها همراه با یک پیام توضیحی.

مثال: git commit -m "افزودن فرم ورود"

Push

فرستادن Commitهای ذخیره‌شده روی کامپیوتر شما، به Repository روی GitHub.

مثال: بعد از چند Commit، با git push آن‌ها را آنلاین می‌کنید.

Pull

دریافت آخرین تغییرات از GitHub و ترکیب آن‌ها با فایل‌های روی کامپیوتر شما.

مثال: همکارتان تغییری Push کرده؛ شما با git pull آن را دریافت می‌کنید.

Clone

کپی کردن کامل یک Repository از GitHub روی کامپیوتر شما، همراه با تمام تاریخچه.

مثال: شروع کار روی یک پروژه تیمی موجود در GitHub.

Branch

یک مسیر جدا از توسعه پروژه؛ اجازه می‌دهد بدون خراب کردن نسخه اصلی روی چیز جدیدی کار کنید.

مثال: ساخت Branch با نام feature/navbar برای طراحی یک منوی جدید.

Merge

ترکیب کردن تغییرات یک Branch با Branch دیگر.

مثال: بعد از اتمام navbar، آن را در Branch اصلی Merge می‌کنید.

Pull Request

درخواستی در GitHub برای این‌که تغییرات یک Branch، بعد از بررسی، وارد Branch اصلی شود.

مثال: در یک پروژه تیمی، قبل از ورود کد به main یک PR باز می‌کنید تا هم‌تیمی‌ها آن را ببینند.

Remote

آدرس یک نسخه از Repository که جایی خارج از کامپیوتر شما قرار دارد؛ معمولاً روی GitHub.

مثال: آدرس https://github.com/USERNAME/MyProject.git یک Remote است.

Origin

نامی پیش‌فرض که Git معمولاً به Remote اصلی شما می‌دهد.

مثال: وقتی می‌نویسید git push origin main، یعنی به همان Remote اصلی بفرست.

HEAD

اشاره‌گری که نشان می‌دهد الان دقیقاً روی کدام Commit یا Branch هستید.

مثال: HEAD~1 یعنی یک Commit قبل‌تر از جایی که الان هستید.

Staging Area

منطقه‌ای موقت؛ فایل‌هایی که با git add به آن اضافه می‌شوند برای Commit بعدی آماده‌اند.

مثال: می‌توانید فقط یک فایل را Stage کنید و بقیه را برای بعد بگذارید.

Working Directory

همان پوشه پروژه روی کامپیوتر شما که فایل‌ها را می‌بینید و ویرایش می‌کنید.

مثال: پوشه C:\xampp\htdocs\MyProject همان Working Directory شماست.

۲

نصب و تنظیم اولیه Git

بررسی نصب بودن و مشاهده نسخه

PowerShell / CMD
git --version

اگر شماره نسخه‌ای مثل git version 2.4x.x نمایش داده شود، Git نصب است. اگر پیام «not recognized» دیدید، باید Git را از git-scm.com نصب کنید.

تنظیم نام و ایمیل

این اطلاعات در کنار هر Commit ذخیره می‌شود تا مشخص باشد چه کسی آن را ساخته است.

PowerShell / CMD
git config --global user.name "Your Name"
git config --global user.email "you@example.com"

مشاهده تنظیمات فعلی

PowerShell / CMD
git config --list

تغییر نام یا ایمیل

کافی است همان دستور --global را دوباره با مقدار جدید اجرا کنید؛ مقدار قبلی جایگزین می‌شود.

PowerShell / CMD
git config --global user.email "new-email@example.com"

تفاوت global و local

Global در برابر Local با --global تنظیمات برای همه پروژه‌های Windows شما اعمال می‌شود (در فایل C:\Users\YourName\.gitconfig ذخیره می‌شود). بدون --global، تنظیمات فقط برای همان Repository فعلی اعمال می‌شود (در .git/config همان پروژه). این برای زمانی مفید است که مثلاً پروژه‌های کاری و شخصی، ایمیل متفاوتی می‌خواهند.
۳

شروع یک پروژه جدید

فرض کنید یک پروژه در مسیر C:\xampp\htdocs\MyProject دارید که هنوز با Git ردیابی نمی‌شود.

C:\xampp\htdocs\MyProject>
git init
git status
git add .
git commit -m "Initial commit"
  • git init — یک پوشه مخفی .git در پروژه می‌سازد و از همین لحظه، Git شروع به ردیابی تغییرات این پوشه می‌کند.
  • git status — نشان می‌دهد چه فایل‌هایی ردیابی نشده‌اند (Untracked)، تغییر کرده‌اند یا Stage شده‌اند.
  • git add . — همه فایل‌های تغییر‌کرده در پوشه فعلی را به Staging Area اضافه می‌کند.
  • git commit -m "Initial commit" — از وضعیت Stage‌شده یک Commit اول با پیام مشخص می‌سازد.
نکتهبعد از هر مرحله، دوباره git status بزنید تا مطمئن شوید دقیقاً چه اتفاقی افتاده — این عادت خیلی از اشتباهات را از ابتدا می‌گیرد.
۴

ساخت Repository در GitHub

چگونه Repository جدید بسازیم

در GitHub روی دکمه New repository بزنید، نامی مثل MyProject انتخاب کنید و Create Repository را بزنید.

Public در برابر Private

Public یعنی همه می‌توانند کد شما را ببینند (خوب برای نمونه‌کار و پروژه‌های متن‌باز). Private یعنی فقط شما و افرادی که دعوت کنید دسترسی دارند (مناسب پروژه‌های شخصی یا کاری).

چه زمانی README بسازم؟

خیلی مهم اگر پروژه‌ای از قبل روی کامپیوترتان دارید (مثل سناریوی این راهنما)، هنگام ساخت Repository گزینه‌های README، .gitignore و License را فعال نکنید. چون این گزینه‌ها یک Commit اولیه در GitHub می‌سازند که با پروژه لوکال شما هم‌تاریخچه نیست و اولین Push شما را با تعارض روبه‌رو می‌کند. اگر پروژه کاملاً خالی و از صفر است، ساختن README هیچ مشکلی ندارد.

gitignore. و License

.gitignore فهرستی از فایل‌ها و پوشه‌هایی است که نمی‌خواهید Git آن‌ها را ردیابی کند (جزئیات کامل در بخش ۱۳). License مجوزی است که مشخص می‌کند دیگران چگونه اجازه دارند از کد شما استفاده کنند؛ برای پروژه‌های شخصی، MIT License انتخاب رایجی است.

۵

اتصال پروژه Local به GitHub

سناریو: پروژه شما در C:\xampp\htdocs\MyProject است و Repository‌تان https://github.com/USERNAME/MyProject.git

C:\xampp\htdocs\MyProject>
git remote add origin https://github.com/USERNAME/MyProject.git
git remote -v
git branch -M main
git push -u origin main
  • git remote add origin ... — به Git می‌گوید آدرس Remote اصلی شما (که از این پس نامش origin است) این است.
  • git remote -v — آدرس‌های Remote تنظیم‌شده را برای بررسی نشان می‌دهد.
  • git branch -M main — نام Branch فعلی را به main تغییر می‌دهد (نام استاندارد Branch اصلی در GitHub).
  • git push -u origin main — Branch لوکال main را به Remote به نام origin می‌فرستد؛ فلگ -u یعنی این دو را به هم «متصل» کن تا دفعات بعد کافی باشد فقط بنویسید git push یا git pull.
Origin و Main دقیقاً چه هستند؟origin فقط یک اسم مستعار برای آدرس طولانی Repository روی GitHub است — می‌توانستید هر اسم دیگری هم بگذارید. main اسم Branch اصلی پروژه شماست؛ همان‌جایی که نسخه پایدار و نهایی کد نگه‌داری می‌شود.

کار روزمره با Git

این پنج دستور، ۹۰٪ کارهای روزانه شما با Git هستند.

C:\xampp\htdocs\MyProject>
git status
git add .
git add filename
git commit -m "..."
git push
git pull

مثال واقعی

فرض کنید فایل index.php را ویرایش کرده‌اید:

C:\xampp\htdocs\MyProject>
git status
git add index.php
git commit -m "اصلاح فرم ورود کاربر"
git push

اگر همکاری روی همین پروژه کار می‌کند، قبل از شروع کار روزانه بهتر است اول git pull بزنید تا آخرین نسخه را داشته باشید.

۷

مشاهده تاریخچه

C:\xampp\htdocs\MyProject>
git log
git log --oneline
git log --oneline --graph --all
git show <commit-hash>
git diff
git diff --staged
  • git log — فهرست کامل Commitها با پیام، نویسنده و تاریخ.
  • git log --oneline — نسخه خلاصه؛ هر Commit در یک خط.
  • git log --oneline --graph --all — نمایش گرافیکی Branchها و نحوه Merge شدن آن‌ها؛ خیلی مفید برای درک وضعیت پروژه.
  • git show <commit-hash> — جزئیات کامل یک Commit خاص، شامل فایل‌ها و خطوط تغییر‌یافته.
  • git diff — تفاوت فایل‌های تغییر‌کرده اما Stage‌نشده، نسبت به آخرین Commit.
  • git diff --staged — تفاوت فایل‌هایی که با git add Stage شده‌اند.
چطور بفهمم چه فایل‌هایی تغییر کرده‌اند؟ساده‌ترین راه git status است. برای یک خلاصه آماری از تعداد خطوط تغییر‌یافته در هر فایل، از git diff --stat استفاده کنید.
۸

برگرداندن تغییرات و Undo

مهم‌ترین سؤال همیشه این است: «الان دقیقاً کجای مسیر هستم؟» جواب، دستور مناسب را مشخص می‌کند.

هنوز Commit نکرده‌ام
برای دور ریختن تغییرات یک فایل خاص: git restore filename
برای دور ریختن همه تغییرات: git restore .
برای خارج کردن فایل از Staging (بدون از دست دادن تغییرات): git restore --staged filename
Commit کرده‌ام، ولی Push نکرده‌ام
لغو آخرین Commit و نگه‌داشتن تغییرات در Staging: git reset --soft HEAD~1
لغو آخرین Commit و نگه‌داشتن تغییرات به‌صورت Unstaged (حالت پیش‌فرض): git reset --mixed HEAD~1
لغو آخرین Commit و حذف کامل تغییرات ⚠️: git reset --hard HEAD~1
Commit را Push هم کرده‌ام
از git revert <commit-hash> استفاده کنید؛ این دستور یک Commit جدید می‌سازد که تغییرات Commit قبلی را خنثی می‌کند، بدون این‌که تاریخچه را پاک کند — امن برای پروژه‌های اشتراکی.

چه زمانی revert بهتر از reset است؟

reset تاریخچه را بازنویسی می‌کند، پس فقط برای Commitهایی مناسب است که هنوز Push نشده‌اند (فقط روی کامپیوتر خودتان هستند). revert تاریخچه قبلی را دست‌نخورده نگه می‌دارد و یک Commit جدید اضافه می‌کند، پس برای هر چیزی که قبلاً Push یا با دیگران به اشتراک گذاشته شده، انتخاب درست و امن است.

⚠️ دستورات خطرناکدقت کنید
git reset --hard
git push --force
هشدار git reset --hard تمام تغییرات Commit‌نشده را برای همیشه پاک می‌کند — قابل بازگشت نیست. git push --force تاریخچه روی GitHub را با نسخه لوکال شما جایگزین می‌کند و ممکن است Commitهای دیگران را پاک کند. اگر باید Force کنید، ترجیحاً از git push --force-with-lease استفاده کنید؛ این حالت اگر کس دیگری تازه چیزی Push کرده باشد، جلوی از دست رفتن کارش را می‌گیرد.
۹

Branch

C:\xampp\htdocs\MyProject>
git branch
git branch branch-name
git switch branch-name
git switch -c branch-name
git checkout branch-name
git merge branch-name
git branch -d branch-name
  • git branch — فهرست همه Branchهای موجود، با علامت روی Branch فعلی.
  • git branch branch-name — ساخت یک Branch جدید (بدون جابه‌جا شدن به آن).
  • git switch branch-name — جابه‌جایی به یک Branch موجود.
  • git switch -c branch-name — ساخت Branch جدید و جابه‌جایی هم‌زمان به آن (معادل قدیمی: git checkout -b).
  • git checkout branch-name — روش قدیمی‌تر برای جابه‌جایی بین Branchها؛ هنوز رایج است.
  • git merge branch-name — تغییرات branch-name را وارد Branch فعلی می‌کند.
  • git branch -d branch-name — حذف یک Branch که کامل Merge شده. برای حذف اجباری Branch Merge‌نشده ⚠️ از -D استفاده کنید.

مثال واقعی: main → development → feature/navbar

C:\xampp\htdocs\MyProject>
git switch -c development
git switch -c feature/navbar
git add .
git commit -m "افزودن navbar"
git switch development
git merge feature/navbar
git branch -d feature/navbar

وقتی development هم پایدار و آماده شد، همین مسیر Merge را از main روی development تکرار می‌کنید.

۱۰

Conflict

وقتی دو Branch یک قسمت از همان فایل را به‌شکل متفاوت تغییر داده باشند، Git نمی‌تواند خودش تصمیم بگیرد کدام درست است — این یعنی Conflict.

مراحل رفع تعارض

C:\xampp\htdocs\MyProject>
git pull
# فایل تعارض‌دار را باز و اصلاح کنید
git add .
git commit
git push

داخل فایل تعارض‌دار، Git بخش‌هایی شبیه این اضافه می‌کند:

index.php
<<<<<<< HEAD
کد نسخه فعلی شما
=======
کد نسخه دریافت‌شده از GitHub
>>>>>>> branch-name

باید تصمیم بگیرید کدام بخش (یا ترکیبی از هر دو) درست است، خطوط <<<<<<<، ======= و >>>>>>> را کامل پاک کنید، سپس فایل را ذخیره کنید.

اگر وارد صفحه Vim شدید

گاهی هنگام git commit یا git merge، یک صفحه متنی مثل این باز می‌شود:

Vim editor
Merge branch 'main'...
خروج از Vimپیام پیش‌فرض معمولاً همان چیزی است که نیاز دارید؛ کلید Esc را بزنید و سپس تایپ کنید :wq و کلید Enter را بزنید تا ذخیره و خارج شوید. اگر خواستید بدون ذخیره خارج شوید: Esc سپس :q!
۱۱

Clone

برای دریافت یک Repository موجود روی کامپیوتر خودتان (مثلاً روی یک سیستم جدید یا برای همکاری در پروژه‌ای تیمی):

C:\xampp\htdocs>
git clone https://github.com/USERNAME/RepoName.git
cd RepoName
code .
  • git clone ... — یک پوشه جدید با نام Repository می‌سازد و کل پروژه + تاریخچه را داخلش کپی می‌کند.
  • cd RepoName — وارد پوشه پروژه می‌شوید.
  • code . — پوشه فعلی را در VS Code باز می‌کند.
۱۲

Remote

C:\xampp\htdocs\MyProject>
git remote -v
git remote add origin https://github.com/USERNAME/MyProject.git
git remote remove origin
git remote set-url origin https://github.com/USERNAME/NewName.git
git fetch
git pull
  • git remote -v — نشان می‌دهد چه Remoteهایی تنظیم شده و آدرس Fetch/Push هرکدام چیست.
  • git remote add origin — یک Remote جدید با نام origin اضافه می‌کند.
  • git remote remove origin — Remote به نام origin را از پروژه حذف می‌کند (پروژه روی GitHub حذف نمی‌شود، فقط اتصال لوکال قطع می‌شود).
  • git remote set-url origin — آدرس یک Remote موجود را تغییر می‌دهد؛ مثلاً وقتی نام Repository عوض شده یا می‌خواهید از HTTPS به SSH سوییچ کنید.
  • git fetch — تغییرات جدید را از Remote دانلود می‌کند اما آن‌ها را با فایل‌های شما Merge نمی‌کند؛ راه امنی برای دیدن چه چیزی جدید است، قبل از Pull واقعی.
  • git pull — دقیقاً معادل fetch + merge در یک مرحله.
۱۳

.gitignore

.gitignore فایلی متنی در ریشه پروژه است که به Git می‌گوید کدام فایل‌ها و پوشه‌ها را اصلاً ردیابی نکند — مثل فایل‌های حساس، کش، یا وابستگی‌های حجیم.

نمونه .gitignore برای پروژه PHP + XAMPP

.gitignore
# محیط و تنظیمات حساس
.env
config.php
wp-config.php

# وابستگی‌ها
/vendor/
node_modules/

# لاگ‌های سرور لوکال
*.log
error_log

# کش و فایل‌های موقت
*.cache
*.tmp
/tmp/

# دامپ دیتابیس
*.sql

# فایل‌های سیستم‌عامل و ادیتور
.DS_Store
Thumbs.db
.vscode/
.idea/

موارد بالا شامل تنظیمات حساس (رمز دیتابیس در .env یا config.php)، وابستگی‌های قابل نصب مجدد، فایل‌های لاگ و کش سرور، و فایل‌های شخصی ادیتور/سیستم‌عامل است که هیچ‌کدام نباید در Repository عمومی باشند.

اگر یک فایل حساس قبلاً Commit و Push شده باشد فقط اضافه کردن آن به .gitignore کافی نیست — فایل همچنان در تاریخچه قدیمی Git باقی می‌ماند. مراحل درست:
C:\xampp\htdocs\MyProject>
git rm --cached .env
# سپس .env را به .gitignore اضافه کنید
git commit -m "Remove .env from tracking"
git push

git rm --cached فایل را از ردیابی Git خارج می‌کند اما نسخه لوکال را روی کامپیوتر شما دست‌نخورده نگه می‌دارد.

نکته امنیتی مهماین کار فایل را فقط از Commitهای بعدی حذف می‌کند؛ در Commitهای قدیمی هنوز قابل مشاهده است. اگر رمز یا کلید واقعی داخل آن فایل بوده و Repository عمومی است، آن را لو‌رفته (Compromised) در نظر بگیرید و هرچه سریع‌تر رمز/کلید را عوض کنید. برای پاک کردن کامل از تاریخچه به ابزارهای پیشرفته‌ای مثل git filter-repo یا BFG Repo-Cleaner نیاز دارید که تاریخچه را کامل بازنویسی می‌کنند (مثل Force Push، نیازمند هماهنگی با تیم).
۱۴

GitHub Authentication

HTTPS در برابر SSH

HTTPS با نام کاربری و یک Personal Access Token (به‌جای رمز عبور واقعی، چون GitHub دیگر رمز ساده را قبول نمی‌کند) وارد می‌شوید؛ ساده‌تر برای شروع. SSH از یک جفت کلید (خصوصی/عمومی) استفاده می‌کند و بعد از تنظیم اولیه، دیگر لازم نیست چیزی وارد کنید؛ برای استفاده روزانه سنگین رایج‌تر است.

روش پیشنهادی برای Windows + VS Code

وقتی Git for Windows را نصب می‌کنید، ابزار Git Credential Manager هم همراهش نصب می‌شود. با روش HTTPS، اولین باری که git push می‌زنید، یک پنجره مرورگر برای ورود به GitHub باز می‌شود؛ بعد از ورود، دفعات بعدی دیگر چیزی از شما نمی‌پرسد. برای اکثر کاربران مبتدی، همین روش ساده‌ترین و کافی‌ترین گزینه است.

در صورت نیاز به SSH اگر بعداً خواستید از SSH استفاده کنید: ssh-keygen -t ed25519 -C "email@example.com" برای ساخت کلید، سپس کلید عمومی را در بخش Settings → SSH and GPG keys حساب GitHub خود اضافه کنید و آدرس Remote را با git remote set-url origin git@github.com:USERNAME/Repo.git به فرمت SSH تغییر دهید.
۱۵

VS Code + Git

پنل Source Control را با کلید میانبر Ctrl + Shift + G باز کنید.

  • Stage کردن: ماوس را روی نام فایل ببرید و آیکون «+» را بزنید؛ یا برای همه فایل‌ها روی «+» کنار عنوان Changes بزنید.
  • Commit کردن: پیام Commit را در باکس بالای پنل بنویسید و آیکون ✓ (Commit) را بزنید.
  • Push و Pull: از منوی «...» بالای پنل Source Control، یا با کلیک روی فلش‌های Sync در نوار پایین پنجره VS Code.
  • ساخت Branch جدید: روی نام Branch فعلی در گوشه پایین‌چپ کلیک کنید و «Create new Branch» را انتخاب کنید.
  • تعویض Branch: همان قسمت پایین‌چپ را باز کنید و از فهرست، Branch مورد نظر را انتخاب کنید.
  • دیدن Conflict: فایل‌های دارای تعارض با یک نشانگر مخصوص علامت‌گذاری می‌شوند؛ VS Code دکمه‌های «Accept Current / Accept Incoming / Accept Both» را مستقیم داخل فایل نشان می‌دهد.
  • بررسی تغییرات: روی هر فایل در پنل Source Control کلیک کنید تا نمای Diff (تفاوت نسخه قدیم و جدید) باز شود.
۱۶

GitHub Workflow حرفه‌ای

Workflow پروژه شخصی

main همیشه پایدار می‌ماند. برای هر قابلیت جدید، یک Branch با نام feature/نام-قابلیت می‌سازید، روی آن کار می‌کنید و وقتی تمام و تست شد، در main Merge می‌کنید.

Workflow پروژه تیمی

سه لایه رایج: main (نسخه نهایی و منتشرشده)، development (محل ترکیب کارهای در حال انجام)، و feature/* (یک Branch به ازای هر کار). هر عضو تیم روی Branch خودش کار می‌کند، سپس یک Pull Request به سمت development باز می‌کند.

چه زمانی Pull Request بسازم؟

هر وقت قرار است کدی قبل از ورود به یک Branch مهم (main یا development) بررسی شود — چه توسط هم‌تیمی‌ها و چه حتی خودتان برای مرور نهایی. PR باعث می‌شود همه تغییرات یک‌جا و قابل بررسی دیده شوند، پیش از این‌که وارد نسخه اصلی پروژه شوند.

سناریوهای واقعی

۱. پروژه جدید دارم و می‌خواهم Git را فعال کنم.

cmd
git init

۲. می‌خواهم پروژه را برای اولین بار به GitHub بفرستم.

cmd
git remote add origin https://github.com/USERNAME/Repo.git
git branch -M main
git push -u origin main

۳. یک فایل تغییر کرده و می‌خواهم Push کنم.

cmd
git add .
git commit -m "توضیح تغییر"
git push

۴. اشتباه کردم و هنوز Commit نکرده‌ام.

cmd
git restore filename

۵. اشتباه کردم و Commit کرده‌ام (ولی هنوز Push نکرده‌ام).

cmd
git reset --soft HEAD~1

۶. Commit اشتباه را Push هم کرده‌ام.

cmd
git revert <commit-hash>
git push

۷. می‌خواهم به نسخه قبلی یک فایل برگردم.

cmd
git log filename
git checkout <commit-hash> -- filename

۸. GitHub از من Pull می‌خواهد و Push انجام نمی‌شود.

cmd
git pull
git push

اگر هنگام Pull تعارض دیدید، مطابق بخش ۱۰ آن را رفع کنید.

۹. Merge Conflict دارم.

cmd
git pull
# فایل را اصلاح کنید
git add .
git commit
git push

۱۰. می‌خواهم پروژه GitHub را روی یک کامپیوتر جدید دریافت کنم.

cmd
git clone https://github.com/USERNAME/Repo.git

۱۱. می‌خواهم قبل از Commit ببینم دقیقاً چه چیزی تغییر کرده.

cmd
git status
git diff

۱۲. می‌خواهم یک قابلیت جدید بسازم بدون این‌که main را خراب کنم.

cmd
git switch -c feature/new-thing

هر روز برای پروژه‌ام چه کار کنم؟

  1. پروژه را باز کنیدترمینال VS Code را در پوشه پروژه باز کنید.
  2. آخرین تغییرات را بگیریدمخصوصاً اگر تیمی کار می‌کنید: git pull
  3. روی کد کار کنیدویرایش، تست و اجرای پروژه روی XAMPP.
  4. وضعیت را بررسی کنیدgit status تا ببینید چه چیزی تغییر کرده.
  5. تغییرات را Stage کنیدgit add .
  6. Commit بگیریدبا پیامی کوتاه و واضح: git commit -m "..."
  7. ارسال به GitHubgit push
  8. در پایان کار روی یک Branchاگر روی Branch جداگانه بودید و کار تمام شد، آن را Merge کنید یا یک Pull Request باز کنید.
